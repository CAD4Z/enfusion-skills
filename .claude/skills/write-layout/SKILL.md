Скилл пишет один `.layout`-файл по описанию пользователя. Работает в связке с другими навыками: `scriptclass`-обёртки, `.styles`-файлы, imagesets и локализация — **вне скоупа**, ссылается на них только по явно названным именам.

## Что скилл делает и не делает

**Делает:**
- Изобретает иерархию виджетов, типы и имена из описания
- Пишет валидный `.layout`-файл в синтаксисе, описанном в `format.md`
- Использует только свойства, задокументированные в референсах

**Не делает:**
- Не спрашивает уточняющих вопросов **до** показа плана
- Не создаёт `.styles`, `.csv`, `.c`, imageset-файлы
- Не пишет свойство, которого нет в референсах (жёсткий стоп, ноль опоры на "память модели")
- Не пишет `style`, `font`, `image`, `scriptclass` — если пользователь не назвал конкретные имена

## Алгоритм

### Шаг 1 — Прочитать `format.md`

Перед любой работой прочитать `.claude/references/DayZ/Layouts/format.md`. Это обязательный шаг, без исключений даже для "пустой панели". Там живут: синтаксис, система позиционирования, все общие свойства (Widget, UIWidget, Text, SpacerWidget, SimpleProgressBarWidget), правила ссылок на ресурсы.

### Шаг 2 — Построить план из описания

Принять описание пользователя как есть, без уточняющих вопросов. Если описание расплывчатое — дополнить разумными умолчаниями (типовая иерархия, очевидные виджеты). Пользователь исправит через цикл итераций.

Определить для каждого виджета:
- **Тип** — наиболее подходящий класс из таблицы в `.claude/references/DayZ/Layouts/.INDEX.md`
- **Имя** — `snake_case` с трёхбуквенным префиксом типа (см. таблицу ниже)
- **Роль** — однострочное описание что это и где

Систему координат, выбор типа контейнера (Grid vs Wrap vs Panel+ручное позиционирование), значения `position`/`size` и прочие детали имплементации — **решать самому**, не выносить в план. Пользователь доверяет этим решениям.

### Шаг 3 — Показать план

Рендерить иерархию как ASCII-дерево через `├─` `└─` `│`. Формат узла: `ТипВиджета имя_виджета — однострочная роль`.

Пример:
```
PanelWidgetClass pnl_main_menu
├─ ImageWidgetClass img_logo — логотип DayZ сверху по центру
├─ GridSpacerWidgetClass spc_buttons — колонка кнопок, центр экрана
│  ├─ ButtonWidgetClass btn_play — "Играть"
│  ├─ ButtonWidgetClass btn_settings — "Настройки"
│  └─ ButtonWidgetClass btn_exit — "Выход"
└─ TextWidgetClass txt_version — версия игры, правый нижний угол
```

Если по описанию подразумеваются ссылки на внешние ресурсы (стили, шрифты, иконки) — добавить **отдельную секцию** "External resources" под деревом с перечнем того, что останется на дефолтах, и предложением указать готовые имена если они есть:

```
External resources (оставлю на дефолтах — назови если есть готовые):
- style для btn_play / btn_settings / btn_exit
- image для img_logo
```

Сразу после плана ждать ответа. **Не писать файл без явного триггера.**

### Шаг 4 — Цикл итераций

Любое сообщение пользователя, не являющееся триггером `пиши` / `ок` / `write` / `yes` / `да`, трактуется как корректирующая правка. Применить правку и **перерисовать весь план заново** (не diff). Ждать следующего ответа.

Если правка физически невыразима в layout-формате (hover-эффекты, анимации, круглая форма, подсветка при наведении и т.п.) — коротко указать **разделение труда**: "это решается через `.styles`-файл, не через layout", и если уместно — добавить заготовку-свойство (`style "btn_round"`) с примечанием что стиль должен быть создан отдельно (через будущий `.styles`-скилл). Не превращать это в новый раунд вопросов.

Если правка требует свойства, которого нет в референсах — сказать об этом честно: "свойства `X` нет в документации DayZ Layouts, писать не буду". Никогда не писать по памяти.

### Шаг 5 — На триггер "пиши" — подгрузить доки и записать файл

1. Собрать множество всех типов виджетов, используемых в финальном плане.
2. По `.INDEX.md` определить какие `widgets_*.md` файлы их документируют.
3. **Прочитать только эти файлы** (не все скопом). `format.md` уже прочитан на шаге 1.
4. Сгенерировать текст файла, следуя правилам codestyle ниже.
5. Определить путь: если пользователь передал явный путь — использовать его. Иначе — `gui/layouts/{имя_корневого_виджета_без_префикса}.layout` (например, `pnl_main_menu` → `gui/layouts/main_menu.layout`).
6. Записать файл.

### Шаг 6 — Пост-валидация

Молча перечитать записанный файл и проверить:
- Один корневой виджет
- Все имена из финального плана присутствуют в файле
- Файл парсится по синтаксису из `format.md` (формально: совпадение скобок, свойства в формате `key value`)

Рапортовать пользователю только если что-то не сошлось. При успехе — короткое сообщение о записанном файле и список ссылок на внешние ресурсы, которые пользователю нужно будет создать/предоставить (если такие были).

| Префикс | Классы |
|---|---|
| `btn` | ButtonWidget |
| `txt` | TextWidget, MultilineTextWidget, RichTextWidget |
| `edt` | EditBoxWidget |
| `img` | ImageWidget |
| `vid` | VideoWidget |
| `pnl` | PanelWidget, SmartPanelWidget |
| `frm` | FrameWidget, ContentWidget |
| `spc` | WrapSpacerWidget, GridSpacerWidget |
| `scr` | ScrollWidget |
| `chk` | CheckBoxWidget, ThreeStateCheckboxWidget |
| `cmb` | XComboBoxWidget |
| `sld` | SliderWidget |
| `prg` | SimpleProgressBarWidget, ProgressBarWidget |
| `itm` | ItemPreviewWidget |
| `plr` | PlayerPreviewWidget |
| `rnd` | RenderTargetWidget, RTTextureWidget |
| `cnv` | CanvasWidget |

Имена — `snake_case`, префикс + подчёркивание + семантика: `btn_play`, `txt_title`, `img_logo`, `spc_buttons`, `pnl_main_menu`.

## Codestyle

**Отступы:** 1 пробел на уровень вложенности. Строго.

**Многословные ключи:** всегда в двойных кавычках, даже если грамматически можно без:
```
"text halign" center
"Size To Content V" 1
"no focus" 0
```

**Порядок свойств внутри виджета** (сверху вниз):
1. Видимость и взаимодействие: `visible`, `disabled`, `clipchildren`, `inheritalpha`, `ignorepointer`, `draggable`, `priority`, `userID`
2. Позиционирование: `position`, `size`, `hexactpos`, `vexactpos`, `hexactsize`, `vexactsize`
3. Выравнивание: `halign`, `valign`, `fixaspect`
4. Цвет и масштаб: `color`, `scaled`
5. Навигация фокуса (UIWidget): `"no focus"`, `"next left/right/up/down"`
6. Специфичные для типа: `text`, `font`, `"text *"`, `"outline *"`, `"shadow *"`, `image0`, `imageTexture`, `mode`, `Padding`, `Margin`, `Columns`, `Rows`, `"Size To Content *"`, `content_halign`, `content_valign`, `minimum`, `maximum`, `current`, `step` и т.п.
7. Стиль: `style` (только если пользователь назвал имя)
8. `scriptclass` — в самом конце (только если пользователь упомянул связь со скриптом)

Дочерние виджеты — после всех свойств, внутри `{ }`.

**Свойства-дефолты не писать.** Если `visible 1` и `disabled 0` — значения по умолчанию, не загромождать файл.

## Правила написания ресурсов

| Ресурс | Когда писать |
|---|---|
| `scriptclass` | Только если пользователь явно упомянул связь со скриптом или назвал имя класса. Иначе опустить. |
| `text` | Писать всегда для виджетов, которым текст подразумевается (кнопки, лейблы). Формат — **буквальная строка** (`text "Играть"`), не `#str_*`-ключи локализации. Пользователь сам заменит на ключ при локализации. |
| `style` | Только если пользователь назвал имя стиля. Иначе опустить (виджет получит `Default`). |
| `font` | Только если пользователь назвал путь к шрифту. Иначе опустить. |
| `image` / `image0` / `imageTexture` | Только если пользователь назвал источник. Иначе опустить (виджет будет пустым). |

**Жёсткий инвариант:** скилл никогда не изобретает имя внешнего ресурса и не пишет плейсхолдер вроде `style "TODO"`. Лучше голый виджет на дефолтах, чем битая ссылка.

## Жёсткий стоп на неизвестные свойства

Если во время написания возникает искушение написать свойство, которого нет в прочитанных `format.md` + соответствующих `widgets_*.md` — **не писать**. Сказать пользователю: "свойство `X` не найдено в документации, добавляю его означало бы опираться на непроверенную память — пропускаю". Это сознательный инвариант качества, не баг.

## Композиция с другими скиллами

Скилл принимает на вход **описание от пользователя** в свободной форме, либо **структурированные данные от другого скилла** (например, будущий PRD-скилл может передать список виджетов напрямую). Во втором случае шаг построения плана сокращается до проверки и рендера, но всё равно проходит через цикл подтверждения.
